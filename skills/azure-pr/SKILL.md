# Azure DevOps PR tooling


Use `pr.sh` from PATH for Azure DevOps pull-request, review-comment, and PR validation-build operations. If `command -v pr.sh` fails, report the install step: `mkdir -p ~/.local/bin && ln -s <checkout>/pr.sh ~/.local/bin/pr.sh`, with `~/.local/bin` on PATH. Alternatively, run `pnpm add --global link:<checkout>` (pnpm 10 and older: `pnpm link --global` in the checkout), with the pnpm global bin directory on PATH. Run it from the root of the target Azure Repos checkout so it can discover the repository, current branch, and active pull request. Use `pr.sh pr list` to list active pull requests created by the authenticated PAT owner in that repository. Add `--reviewing` to list active pull requests assigned to that identity, `--all` to list every active pull request, or `--target <branch>` to filter by target branch. `--reviewing` and `--all` cannot be combined. Human output includes draft state and reviewer votes; `--json` returns raw data. Use `pr.sh pr diff [--pr <id>] [--since-iteration <n> | --since-last-review] [--name-only] [--json]` to read a pull request's changes from Azure DevOps as a unified diff, without fetching the branch. The unified diff's first line names the latest iteration, and `--json` has it in `iteration`; note it after a review and pass it as `--since-iteration` next time to see only what changed since then. `--since-last-review` picks that iteration for you: the latest one created before your newest comment or vote on the PR. It is a heuristic and fails when you have no such activity, so fall back to `--since-iteration` then. A reply you post after a new push, without reading that push, moves the cutoff past it, so note the iteration when the push matters. `--name-only` prints only one line per changed path, the change type (add, edit, delete or rename), a tab and the path, without reading content; start there on large PRs. `--json` returns `pullRequestId`, `iteration`, `baseIteration`, `lastReview`, `truncated` and `files` with `path`, `originalPath`, `change`, `content` and line `blocks` holding the `removed` and `added` lines; with `--name-only` the files keep only paths and change. Binary files are listed without content. The unified diff stops at 100,000 bytes with a truncation notice. JSON keeps file content within 100,000 bytes but always lists every file, so a pull request with very many files can produce more; it marks a file whose content doesn't fit `content: "omitted"` and sets `truncated: true`. Read such a file with the unified diff or locally. For build inspection/retry/wait use the resource-first `pr.sh build ...` commands; CLI help is the source of truth for their routes, flags, validation, and output. Do not duplicate complete help here. `build show` and `build wait` require either `--build <id>` or `--latest`. The latter selects the newest build validating the PR head across PR merge and source-branch runs. If none validates it, show prints the newest associated build marked stale and exits 1; wait fails naming the head. `build list` also shows branch builds on the PR head, labelled and marked current; see its help for the views. `pr.sh build wait --build <id>` monitors metadata only for a current or historical associated build; `--pr` only selects or resolves its pull request. After bounded PR resolution, it polls every 60 seconds for up to 1 hour by default (`--interval` is 10–3600 seconds; `--timeout` is 10–86400 seconds). Progress and five-minute heartbeats go to stderr. Completed/timed-out waits emit one final human or pretty JSON result to stdout; errors and signals emit none. JSON retains raw Azure build metadata, so inspect it before persistence. Success exits 0, timeout 124, other outcomes/errors 1, SIGINT 130, and SIGTERM 143. Transient poll requests retry, but the third consecutive failure aborts. Waiting never retries/requeues the build, mutates it, or fetches logs—use `build show` afterward for diagnostics. `pr.sh build queue (--pr <id> | --branch <name>) [--definition <id>]` starts a validation build and prints its build ID, build pipeline and URL. `--pr` requeues the PR's build policy evaluation, so the run counts toward the required check; `--branch` queues the build pipeline from the repository's build policy. Add `--definition <id>` (the build pipeline's definition ID) when the repository has several build policies or none. With `--pr` it selects the evaluation for that build pipeline and fails, listing the candidates, if none matches. With `--branch` it queues that build pipeline directly. Check the printed build pipeline name, because a `--definition` from another repository is not validated. A queued build prints a ready-to-run `build wait --build <id> --pr <n>` line. A branch build gets one only when the branch has an active pull request, because `build wait` needs one. If Azure does not return the build ID after a `--pr` requeue, run `build show --latest --pr <n>` until it shows a new build ID, then wait for that ID. A 401, 403, 400 or 404 means nothing was queued; 401 and 403 name the Build (Read & execute) scope. Any other failure after dispatch may still have queued a build, so inspect before retrying.
Use `pr.sh pr status [--pr <id>] [--json]` to check whether a PR is ready in one call instead of combining `pr show`, `build list` and `comment list`. It prints the draft state, the head and merge commits, the latest iteration number, the build validating the head (or a stale marker, or none), the Copilot review line, the unresolved thread count, the merge status with conflicting file paths, a `Blocked by:` line and reviewer votes with `(required)` flags. `Blocked by:` lists the blocking branch policies that are neither approved nor not applicable, as `<policy> (<status>)`, or `none`. `--json` prints the same fields as one JSON document with the keys `id`, `title`, `state`, `draft`, `url`, `headCommit`, `mergeCommit`, `iteration`, `build` (`id`, `number`, `status`, `result`, `sourceVersion`, `association`, `validatesHead`, or `null`), `copilot`, `unresolvedThreads`, `mergeStatus`, `conflicts` (`kind` is `none`, `listed` with `conflicts` as `path` and `type`, or `unavailable` with `error`), `blockingPolicies` (`kind` is `listed` with `policies` as `name` and `status`, or `unavailable` with `error`) and `reviewers` (`name`, `vote`, `voteLabel`, `required`). Missing values are `null`, including `copilot.text` and `copilot.date`, and `iteration` when the iterations cannot be read. Stale and missing builds still exit 0, so read the Build line or `build.validatesHead`. If the iterations, policy evaluations or conflicts cannot be read, the command still succeeds and says so. The Copilot line is best effort: it reports the newest PR timeline entry that mentions a Copilot review as `requested` or `completed` with its date, or `none`. Other wording, such as a cancellation, appears as quoted text with its date. Copilot never votes. Treat `none` as unconfirmed rather than proof that no review ran. The command needs Build (Read) for the build lookup.

Use `pr.sh pr vote --vote approve|approve-with-suggestions|wait|reject|reset [--pr <id>]`, `pr.sh pr abandon [--pr <id>]` and `pr.sh pr reactivate --pr <id>` only when the user asks for that action. A vote sets the authenticated user's own vote and adds them as a reviewer if needed; never vote on the user's behalf unprompted. `reactivate` undoes `abandon` but requires `--pr`, because abandoned PRs are not found from the current branch. If Azure rejects a request, such as reactivating a completed PR, the error includes Azure's status and message.

Complete a pull request only when the user asks for it. Run `pr.sh pr status` first and check the head commit, builds, blocking policies and conflicts. Then run `pr.sh pr complete --merge-strategy merge|squash|rebase|rebase-merge [--delete-source-branch] [--auto] [--pr <id>]`. `--merge-strategy` is required because Azure DevOps does not apply the repository default when no strategy is sent. If the user didn't name a strategy, ask. The command completes the PR at the head commit it just read. It keeps completion options set earlier, for example in the web UI, and the flags given replace only their own options. Azure may still be merging when the command returns; the output then says so, and `pr status` shows the result. A merge that fails afterwards with conflicts, a policy rejection or another failure prints Azure's reason and exits 1. When builds or other policies are still running, suggest `--auto` to the user instead of choosing it yourself. With `--auto`, Azure completes the PR once the required policies pass, at whatever head passes them, including commits pushed later. The command does no pre-check. If Azure rejects the request, it prints Azure's message and suggests `pr status`. After a timeout or network failure the request may have been applied, so run `pr status` before you retry.

Treat the tool's current CLI help as the source of truth for actions, options, validation, authentication, batch schemas, and output. Do not duplicate that reference in this skill. Use `pr.sh --help`; if authentication is not configured yet, run the `src/pr.ts` entrypoint with `--help` instead.

Use `pr.sh pr attach <path> [--name <file name>] [--pr <id>]` to upload any file as a pull request attachment. It prints the URL and a Markdown link. If Azure rejects a filename, the error includes Azure's status and message and suggests trying a different name, such as `--name attachment.txt`. PR descriptions are limited to 4,000 characters, including generated image Markdown. Image uploads use a bidirectional description-placeholder contract: every supplied image needs a matching `{{image:<basename>}}`, and every such placeholder needs a corresponding `--image`. For example, `--description 'Flow: {{image:flow.png}}' --image ./docs/flow.png` uploads the basename `flow.png` and replaces every matching placeholder with rendered image Markdown plus an invisible ado-pr ownership marker. Repeat `--image` and `--reviewer` for multiple values. Uploads reject case-sensitive collisions with existing attachment `displayName` values; replacement is not supported. On `pr edit`, `--remove-image flow.png` removes only exact generated Markdown-and-marker sequences before deleting that exact attachment. Keep the marker unchanged for automatic reference removal. If it is edited or removed, attachment deletion retains the custom reference, which may then be broken. `--remove-reviewer 'Ada Lovelace'` removes the uniquely resolved current reviewer. Quote reviewer display names containing spaces.

Image/reviewer edits can span multiple Azure requests. The tool validates everything it can before mutation and attempts to clean up safely identifiable attachments when an upload-stage failure occurs. A final description-update failure has an uncertain server outcome, so newly uploaded attachments are retained to avoid breaking a possibly applied description; this can leave an orphan attachment. Other later Azure failures can still leave a partially applied edit. Inspect the PR before retrying. The PAT needs Code (Read & Write) for PR/comment mutations. Build commands need Code (Read) for PR metadata; build queries additionally need Build (Read), also named `vso.build`, and build retries and queueing need Build (Read & execute), also named `vso.build_execute`. A 401 or 403 from a build retry or queue names that scope. The policy evaluation requeue scope has not been verified with a real PAT. Build commands support YAML and classic Build API validations, not Releases, external status checks, or individual stage/job/task retries. Diagnostic output defaults to the final 200 log lines; `--full-logs` explicitly requests complete logs and must be treated as potentially sensitive. Only reviewer additions with `--reviewer` on `pr create` or `pr edit` additionally need Identity (Read), also named `vso.identity`; `--remove-reviewer` resolves current PR reviewers and needs only Code (Read & Write).

Use `--attachment <path> [--attachment-name <file name>]` on `pr.sh comment create` or `pr.sh comment reply` to attach one file to a comment. Azure DevOps has no comment attachments, so the tool uploads the file as a pull request attachment and appends its Markdown link to the message after a blank line; the link therefore comes after any AI disclosure in `--message`. If the file cannot be read or the upload fails, nothing is posted. If posting fails after the upload, the error prints the uploaded link: reuse it in the retry instead of uploading again. `--status` and `--attachment` combine on `comment reply`: the reply with the link is posted first and the status is set afterwards. If only the status update fails, the reply and its attachment stay posted and the error says so; do not post them again. Batch operations do not support attachments.

Try to combine as many requests as possible with `pr.sh comment batch` to avoid frequent authentication calls (for example, when the user is using the 1Password integration). Batch input uses qualified `command` values such as `comment.create`, `comment.reply`, and `comment.edit`; consult `--help` for the current schema. To answer and close a thread in one step, use `pr.sh comment reply --status <status>` or the optional `status` field of `comment.reply` and `comment.resolve`; accepted statuses are `fixed`, `wontFix`, `byDesign` and `closed`. A failed status update leaves the reply posted. `comment.reopen` reopens a thread in a batch.

## Disclose AI authorship

Every PR comment whose content is written or rewritten by an agent must disclose the AI authorship and the actual model used. This applies to:

- New threads created with `pr.sh comment create`.
- Replies created with `pr.sh comment reply`.
- Comment content replaced with `pr.sh comment edit`.
- Every `pr.sh comment batch` operation containing a `message` (`comment.create`, `comment.reply`, or `comment.edit`).

Append the disclosure on its own lines after the comment content:

```text
---
🤖 Written by an AI agent (<actual model name>).
```

Replace `<actual model name>` with the exact provider and model identity currently executing the turn, obtained from runtime/session metadata. Never infer, guess, or copy the model name from an existing PR comment, an earlier agent message, the branch, or a default value; different comments may have been written by different models. If the runtime does not expose the exact model identity and it cannot be determined reliably, leave the model name out entirely and post only the rest of the disclosure:

```text
---
🤖 Written by an AI agent.
```

Do not ask the user for the model name and do not use an unverified one; the model name is optional, the AI-authorship disclosure is not. When editing a comment, ensure the resulting content contains one current disclosure rather than dropping it or adding duplicates. Never post or edit agent-authored comment text without the disclosure.

Operations that do not write comment content, such as `pr.sh comment delete`, `pr.sh comment resolve`, `pr.sh comment reopen`, `comment.delete`, `comment.resolve`, and `comment.reopen`, do not require a disclosure.
